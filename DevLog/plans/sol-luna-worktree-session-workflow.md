# Session 任务流选择、Sol/Luna 协作与统一 QA 集成工作流

- 建立日期：2026-08-29
- 最后修订：2026-08-30
- 状态：作为后续开发 Session 的任务分级、执行、审查、QA 与集成基线；每个具体 Session 仍由老大最终选择任务流和模型。
- 适用项目：RainsenVampSur

## 1. 目标与原则

本工作流的目标是在交付质量、上下文连续性、额度消耗和 Unity 工程隔离之间取得平衡。多模型、多任务和 Worktree 都是按风险选用的工具，不是每个 Session 必须执行的固定仪式。

核心原则：

1. Plan 必须先判断任务重量并推荐路线，老大决定实际走 A、B 或 C。
2. 默认使用满足风险要求的最轻流程，避免为轻量功能重复读取项目、传递长交付包和多次完整复测。
3. `main` 始终是已集成、可追溯的权威分支；未批准实现不得直接污染 `main`。
4. 普通串行迭代复用一个长期统一 QA 检出目录，不为每个 Session 复制完整 Unity 项目。
5. 临时 Worktree 只用于高风险独立审查、真实并行任务或 QA 检出无法安全复用的例外。
6. 模型角色必须与任务真实配置一致；不能只通过标题、提示词或分支名自称 Sol/Luna。
7. 任何路线都必须保留冻结范围、可审查提交和与风险相称的验证证据。

OpenAI Docs 对 Worktree 的定义是：同一 Git 仓库的第二份完整检出，每份 Worktree 拥有自己的项目文件，但共享 Git 提交与分支元数据。因此 Worktree 适合并行隔离，不应默认当作每次迭代都要新建的免费环境：

- https://learn.chatgpt.com/docs/environments/git-worktrees

## 2. 术语与三条任务流

### 2.1 术语

- 项目 Session：一个完整、可归档的开发阶段，例如 Session 15。
- Plan 任务：负责只读理解、冻结需求、重量判断、路线推荐、协调与最终集成。
- Execute 任务：在批准范围内实现、测试、提交，并处理后续返工。
- Review：对冻结要求、真实 Diff、Unity 资产和验证证据做准入判断；可以由原 Plan 任务承担，也可以建立独立任务。
- 统一 QA 构筑：长期保留的一份 Unity 项目 Git 检出，用于实现、导入、自动化和人工复测，不是权威生产分支。
- 临时 Worktree：为独立 Review、并行任务或特殊隔离创建的短期完整检出。
- 短期分支：保存 Session 提交、供审查和 fast-forward 合入 `main` 的 Git 锚点。

### 2.2 路线 A：轻量单任务

```text
Session X / Sol
Plan → 老大确认 → Execute → 自审 → 验证 → 集成与归档
```

- 默认模型：`gpt-5.6-sol` / `xhigh`。
- 同一任务保留完整上下文，在统一 QA 构筑中完成实现和自审。
- 不创建 Luna Execute 或独立 Review 任务。
- 适合纯文档、小型数据调整、低耦合逻辑、少量文件且有成熟回归测试的功能。

### 2.3 路线 B：中量双任务

```text
Session X / Plan    —— Sol，负责规划、Review、集成与归档
Session X / Execute —— 默认 Luna，在统一 QA 构筑中实现、验证和全部返工
```

- Plan 默认：`gpt-5.6-sol` / `xhigh`。
- Execute 默认：`gpt-5.6-luna` / `max`；老大可以自由指定其他模型和推理强度。
- 原 Plan 任务审查 Execute 的完整 Diff，不再默认创建第三个 Review 任务。
- 所有返工复用原 Execute 任务、统一 QA 目录和同一短期分支。
- 这是普通功能迭代的推荐路线。

### 2.4 路线 C：重量独立审查

```text
Session X / Plan    —— Sol，负责规划、协调与集成
Session X / Execute —— 默认 Luna，在统一 QA 构筑中实现和返工
Session X / Review  —— Sol，在独立临时 Worktree 中只读审查
```

- 默认 Review：`gpt-5.6-sol` / `xhigh`。
- 独立 Review 从 Execute 最终提交创建 detached Worktree 或临时 Review ref。
- 适合存档迁移、账号状态、跨世界所有权、共享对象池、ProjectSettings、复杂场景/Prefab、大范围架构改造、弱可测试功能或其他高风险改动。
- 路线 C 以更高额度和磁盘成本换取独立上下文与独立验证，不应因习惯自动启用。

## 3. Plan 重量判断与老大决策门

### 3.1 Plan 必读范围

Plan 至少重新读取：

- `CLAUDE.md`
- `DevLog/conventions/agent-workflow.md`
- `DevLog/conventions/project-engineering.md`
- 上一 Session 三份归档
- 当前源码、场景、Prefab、数据资产和 Git 状态

### 3.2 重量判断标准

重量由真实工程影响决定，不能只看玩家描述是否简单，也不能只按文件数量机械分类。

#### 轻量

- 影响单一模块，公共契约和生命周期不变。
- 不涉及存档、跨世界状态、共享对象池、ProjectSettings 或复杂 Unity 序列化。
- 失败后容易定位和回退。
- 已有测试可以直接证明核心行为。

#### 中量

- 涉及多个运行时类、数据资产、Prefab 或新的测试夹具。
- 存在对象池复位、碰撞、输入、UI 焦点、场景绑定或资源导入边界。
- 主要风险可通过清晰 Diff、自动化和人工复测控制。
- 适合让执行模型承担实现，再由原 Plan 任务审查。

#### 重量

- 修改存档结构、迁移、账号权威状态或不可逆数据。
- 修改跨世界所有权、共享对象池核心、ProjectSettings、碰撞矩阵或大范围 Scene/Prefab 结构。
- Diff 较大、依赖链复杂、自动化难以直接证明，或失败影响多个既有系统。
- 需要独立上下文降低自审偏差，或老大明确要求独立 Review。

Session 15 的玩家目标只是“远程敌人”，但实际触及 25 个文件、共享对象池、跨世界所有权、碰撞矩阵和 Prefab 序列化，因此工程重量高于功能描述。

### 3.3 Plan 固定输出

```text
任务编号：
任务目标：
当前状态：
需求边界：
任务重量：轻量 / 中量 / 重量
推荐路线：A / B / C
推荐依据：
预计影响文件与系统：
允许修改范围：
明确禁止范围：
架构与逻辑流程：
验收标准：
自动化验证：
人工复测：
建议 Execute 模型与推理强度：
流程升级条件：
风险、假设与未决问题：
```

Plan 只能推荐，不能代替老大决定。老大可以用简短指令选择：

- `走 A`
- `走 B，Execute 用 Luna/max`
- `走 C，Execute 改用 Sol/high`

老大明确确认路线和冻结契约后才能写入文件。若执行期间发现实际范围超过原重量，例如轻量任务必须修改存档、ProjectSettings 或共享对象池，Execute 必须暂停并申请升级任务流，不得自行扩张。

## 4. 统一 QA 构筑

### 4.1 目录职责

项目长期保留两类检出：

```text
原始 main 检出
└─ 权威 main、最终集成、归档、push；功能批准前保持稳定

统一 QA 检出
└─ Session 短期分支、Unity 导入缓存、实现、自动化与人工复测
```

统一 QA 检出应注册为 Codex 可直接选择的本地项目。它复用自己的 `Library`、`Temp` 和导入缓存，减少每个临时 Worktree 第一次打开 Unity 时产生的完整复制、导入和许可证成本。

统一 QA 构筑不是：

- 第二个长期权威分支。
- 可以积累未提交修改的杂物目录。
- 多个 Session 同时写入的并行环境。
- `main` 的替代品。

### 4.2 每个 Session 的 QA 启动门禁

1. 关闭该 QA 目录上的 Unity、CrashHandler 和测试进程，确认没有有效项目锁。
2. 检查 QA 工作区 tracked/untracked 状态；必须干净。
3. 确认上一 Session 短期分支已集成或已明确保留，QA 分支不存在未处理的独有提交。
4. 读取原始 `main` 的准确 HEAD，作为本 Session 冻结基线。
5. 在 QA 检出切换或创建 `codex/session-X-简短主题` 短期分支，并确认 HEAD 等于冻结基线。
6. 再次确认原始 `main` 工作区干净。

若 QA 目录存在来源不明修改、分支分叉、未集成提交或活动 Unity 锁，必须停止并通知老大。不得用 `git reset --hard`、强制切换或删除 Library 来掩盖状态。

### 4.3 QA 使用边界

- 同一时刻只允许一个写入任务和一个 Unity 实例使用统一 QA 检出。
- 路线 A 的 Sol 任务可以直接在 QA 项目完成全部阶段。
- 路线 B/C 的 Execute 任务使用 QA 项目；原 Plan 任务通过共享 Git 提交在 main 检出审查 Diff。
- 忽略目录中的 Unity 缓存可以跨 Session 保留；只有确认缓存损坏时才按精确路径清理。
- 正式验证报告必须记录命令、测试数量和报告路径；缓存存在不等于可以复用旧测试结论。
- QA 中的人工改动必须提交到当前 Session 分支或明确丢弃，不能无记录带入下一 Session。

### 4.4 允许创建临时 Worktree 的情况

- 路线 C 的独立只读 Review 需要在最终提交上复跑 Unity。
- 两个真正独立的 Session 必须并行推进。
- QA 检出被合法长期任务占用。
- 需要从特定历史提交复现问题，且不能扰动当前 QA 分支。

临时 Worktree 只在确认 `main` 与远端都包含最终提交、且其中没有未保存工作后清理。

### 4.5 Session 收尾后的 QA 停泊

1. 确认当前 Session 分支已经 fast-forward 合入 `main` 并成功推送。
2. 确认 QA 工作区干净、Unity 已关闭、没有残留锁和未跟踪交付文件。
3. 将 QA 检出切回专用停泊分支，例如 `codex/qa`。
4. 仅在停泊分支没有独有提交时，将其 fast-forward 到最新 `main`。
5. 保留 QA 目录和 Unity 缓存，供下一 Session 复用。

若停泊分支无法 fast-forward，不得强制覆盖；先检查是否存在尚未集成的有效提交。

## 5. 按路线执行

### 5.1 路线 A

1. Sol 在统一 QA 构筑完成只读 Plan。
2. 老大确认冻结方案后，同一任务进入 Execute。
3. 只修改批准范围，运行相关测试并提交短期分支。
4. 同一 Sol 任务执行一次基于真实 Diff 的自审；不能只复述自己的实现总结。
5. 自审通过后完成集成前门禁、归档、fast-forward 和 push。

### 5.2 路线 B/C 创建 Execute 任务

Plan 任务按以下顺序创建 Execute：

1. 记录冻结基线并确认 main、QA 都满足启动门禁。
2. 使用 Codex 的“创建新任务”能力创建侧边栏真实任务，目标项目为统一 QA 检出。
3. 默认创建参数：

| 参数 | 默认值 |
| --- | --- |
| 标题 | `Session X / Execute` |
| 项目 | 统一 QA 项目 |
| 环境 | Local QA 检出；只有例外才使用临时 Worktree |
| 起始状态 | 冻结契约中的准确基线提交 |
| 模型 | `gpt-5.6-luna`，允许老大覆盖 |
| 推理强度 | `max`，允许老大覆盖 |
| 初始提示 | 完整冻结契约、规范路径、批准/禁止范围、验证与停止条件 |

4. Execute 开始写入前验证：

- 侧边栏真实出现独立任务。
- 实际模型和推理强度与老大选择一致。
- 工作目录是统一 QA 检出，不是原始 main。
- `git rev-parse HEAD` 与冻结基线一致。
- main 与 QA 在写入前均干净。

任一条件无法验证时立即停止。Plan 不得在未告知老大的情况下自行接管实现，也不得用角色标题冒充模型配置。

5. Plan 必须持有 Execute 的真实任务 ID，并负责完成状态接回：

- Execute 仍在运行时，Plan 使用 Codex 的任务等待能力持续等待 `completed` 或 `needs attention`，不能只确认启动门禁后就结束自己的回合。
- `needs attention` 时由 Plan 汇总阻塞并向老大请求必要决策；普通进度不要求老大手动转述。
- `completed` 时由 Plan 自动读取最终交付包，进入本路线规定的 Review；桌面通知只作为辅助提示，不能替代任务状态接回。
- 用户消息或应用事件中断一次等待后，Plan 处理完新输入应继续等待原 Execute，除非老大明确取消或替换任务。
- 只有 Execute 已完成、已明确阻塞或老大要求暂停时，Plan 才结束该协调阶段。

### 5.3 Execute 要求

1. 复述 Task ID、基线、批准文件和验收标准。
2. 只修改批准范围，不顺手重构无关代码。
3. 对变化按第 7 节偏差规则分类。
4. 运行要求的 EditMode、PlayMode、静态检查和人工可复测清单。
5. 提交当前 Session 短期分支，并输出一次完整交付包。
6. 报告实际模型、推理强度、QA 路径和最终提交；无法读取实际模型时不得声称自己是 Luna。

## 6. Review、返工与额度控制

### 6.1 三种 Review

- 路线 A：同一 Sol 任务依据冻结方案和真实 Diff 自审。
- 路线 B：回到原 Plan 任务审查 Execute 分支；不新建 Review 任务。
- 路线 C：创建 `Session X / Review` 独立只读任务，从 Execute 最终提交建立临时 Worktree。

任何 Review 都必须依据：

```text
冻结方案：预期做什么
Git Diff：实际上做了什么
测试证据：行为是否得到验证
偏差清单：为什么与方案不同
```

不得用 Execute 的成功总结替代源码和 Unity 资产审查。

### 6.2 Finding 是否阻断

- P0/P1：必须阻断集成并返工。
- P2 实际生产缺陷、资产损坏、关键冻结要求缺失：默认阻断。
- P2 仅为未来回归覆盖不足：Review 必须说明当前产品是否已知错误、未来影响和补测成本；可由老大决定立即返工或登记 QA 债务。
- P3 或不影响当前正确性的建议：默认不阻断，进入后续 Todo。

Review 不得只给优先级标签，必须区分“当前真实缺陷”和“测试保护缺口”。

### 6.3 返工与复审

- 所有返工回到原 Execute 任务、统一 QA 检出和同一短期分支。
- 生产代码、Prefab、数据或 ProjectSettings 变化后，运行受影响测试；高风险变化再跑完整门禁。
- 仅测试断言或夹具变化时，优先运行目标测试和相关平台，不为几行测试修改自动重跑一轮完整独立审查。
- 第一次 Review 检查完整 `基线..最终提交`；后续复审默认只检查 `上一已审提交..新提交` 的增量，同时确认既有 Finding 没有引入覆盖回退。
- 最终完整门禁保留两次上限：Execute 交付前一次，main 集成后一次。路线 C 首次独立 Review 确有必要时可以增加一次。
- 微小返工交付只发送增量包，不重复完整长报告。

增量包格式：

```text
Finding ID：
上一提交：
新提交：
实际修改文件：
修复证据：
验证命令与报告：
工作区状态：
READY_FOR_REREVIEW
```

## 7. 执行偏差分级

### A 级：允许执行任务自主调整

- 不改变玩家可见行为的内部实现细节。
- 不改变公共契约的小型类拆分、命名修正或测试夹具调整。
- 保持数据格式、场景结构和验收结果不变的最小正确修复。

在最终变更清单中说明即可。

### B 级：允许继续，但必须登记偏差

- 文件组织、组件边界或 UI 作者方式明显变化。
- 为满足同一验收标准而更换实现模式。
- 增加必要测试、兼容路径或低风险工程保护。

必须分配 `D-01`、`D-02` 等编号，记录原方案、实际实现、原因、影响、验证和建议结论。

### C 级：必须暂停并请求确认

- 改变玩家可见规则、数值、解锁条件或交互语义。
- 改变存档结构、迁移策略或数据所有权。
- 改变 Scene/Prefab 总体结构或引入新依赖。
- 删除功能、扩大范围或无法达到原验收标准。
- 实际工程重量超过已确认路线。
- 当前工作区与冻结基线不一致。

## 8. Execute 最终交付包

Execute 的最终回复是审查索引，不是正确性的唯一证明。路线 B/C 首次交付使用以下结构；路线 A 可在同一任务中保留等价的精简记录。

```markdown
# Session X 执行交付

## 1. Git 信息
- 基线提交：
- 执行分支：
- 最终提交：
- 工作区是否干净：

## 2. 总体结论
- 完成状态：
- 是否建议进入 Review：
- 阻塞项：

## 3. 方案完成矩阵
| 方案项 | 状态 | 实现位置 | 验证证据 | 偏差编号 |
| --- | --- | --- | --- | --- |

## 4. 方案偏差
- 编号、原方案、实际实现、原因、影响、验证和建议结论。

## 5. 变更清单
- 新增、修改、删除、Unity 序列化、存档兼容性。

## 6. 验证证据
- 命令、测试数量、静态检查、报告路径、跳过项及原因。

## 7. 人工复测建议
- 必测、高风险边界、无法自动验证。

## 8. 已知问题与后续项
- 已知限制、未解决问题、范围外发现。

## 9. Review 热点
- 高风险文件、关键决定、建议重点检查。
```

永久事实进入正式 DevLog。禁止用“测试全部通过”代替命令、数量、报告路径和跳过项。

## 9. 集成、归档与 GitHub

满足所选路线的 Review 结论后，由原 Plan/协调任务集成。Execute 和独立 Review 不自行合入 main 或 push。

合入门禁：

- 所选路线的 Review 已通过，或老大明确接受登记的 QA 债务。
- 自动化门禁与人工复测达到冻结要求。
- 原始 main 干净，且没有未审查的新提交。
- Execute 分支是 main 的可验证后继。

归档与推送门禁：

- main 集成后完整门禁通过。
- 三份 Session 归档与实际源码、验证结果和最终提交一致。
- 提交范围只包含当前 Session 的功能、测试、资源和文档。

单开发方默认：

```text
Execute 分支提交
→ 原始 main fast-forward
→ main 集成后完整门禁
→ 三份归档与 Git 状态检查
→ 普通 commit
→ push origin main
→ 验证远端包含最终提交
→ 停泊统一 QA、按条件清理临时 Worktree
```

禁止 force push、历史重写和破坏性清理。短期分支与临时 Worktree 只在 main 和远端都包含最终提交后清理。

## 10. Worktree、分支与 Handoff 边界

- Codex 任务、Git 分支和 Git Worktree 是三层不同概念。
- 手动创建 Worktree 不会创建侧边栏任务，也不能证明实际使用了某个模型。
- 统一 QA 是长期目录；短期分支仍按 Session 创建和提交。
- main 在功能批准前保持稳定，最终只接受已审查提交。
- Handoff 移动同一个任务及其环境，不会把隐式推理自动注入另一个任务。
- 多模型交接默认使用冻结方案、提交 SHA、真实 Diff 和验证证据。
- 只有需要同一任务切换 Local/Worktree 环境时才使用 Handoff。

## 11. 新任务启动提示

### Plan

```text
请完整读取项目规范、上一 Session 三份归档、当前源码和 Git 状态。
本轮先只读规划，不修改文件。请判断任务为轻量/中量/重量，推荐 A/B/C 路线，

等待老大明确选择路线并确认冻结契约后再执行下一阶段。
```

### Execute（路线 B/C）

```text
请读取项目规范、已确认的 Session X 冻结契约和目标文件。
先报告任务标题、实际模型、推理强度、统一 QA 路径、分支和 HEAD；
任一项与冻结契约不一致时停止。只修改批准范围，发现 C 级偏差或重量升级立即暂停。
完成后运行要求的验证、提交 codex/session-X-* 短期分支，并输出一次完整交付包。
后续返工继续复用本任务和分支，只输出增量交付包。
```

### 独立 Review（仅路线 C）

```text
请读取 Session X 冻结方案和 Execute 交付包，独立检查基线到最终提交的完整 Diff。
确认临时 Review Worktree 的 HEAD 等于 Execute 最终提交；默认只读，不直接修复。
区分当前生产缺陷与测试覆盖缺口，说明阻断必要性、未来影响和严重性。
首次审查按风险复跑门禁；返工后优先只审增量和相关测试。
最终输出 APPROVED、CHANGES_REQUESTED 或 BLOCKED_BY_DECISION。
```

## 13. 历史校准

### Session 14

Session 14 在单一 Worktree 中完成实现、反馈修正、自动化和人工复测。该阶段证明短期分支和 fast-forward 可以保持 main 稳定；长期统一 QA 方案在 Session 15 复盘后才正式成为普通串行迭代的推荐环境。

### Session 15

Session 15 同时验证了多任务隔离的价值与成本：

- 首次手动创建 Git Worktree 但没有侧边栏独立 Execute，不能证明使用了指定 Luna 模型。
- 后续真实使用 `gpt-5.6-luna` / `max` Execute 与独立 Sol Review，Review 确实发现了 Prefab 序列化缺陷和测试覆盖不足。
- 正式 Review 共三轮，前两轮为 `CHANGES_REQUESTED`，第三轮 `APPROVED`；第二轮仅恢复一条最大射程测试覆盖，却仍产生完整交接与复审成本。
- 玩家视角的小功能最终触及 25 个文件、对象池、跨世界所有权、ProjectSettings 和 Unity 资产，因此 Plan 必须按真实工程影响而不是标题分级。
- 独立 Review 不是默认必需；轻量走 A、中量走 B、重量走 C，最终由老大选择。
- 长报告、重复完整门禁和多任务上下文重建会抵消便宜执行模型的额度优势；返工后应优先增量复审。
- 普通串行 Session 复用统一 QA 检出，只有高风险独立审查和并行任务使用临时 Worktree。

永久结论：任务流服务于风险控制，不能让流程成本超过功能本身。
