# Session 执行、子 Agent 协作与 QA 工作流

- 建立日期：2026-08-29
- 最后修订：2026-09-13
- 状态：现行协作规则；取代以 A/B/C 固定绑定任务重量、模型和会话数量的旧流程。
- 适用项目：RainsenVampSur
- 授权、测试和版本控制的统一依据：[Agent 协作规范](../conventions/agent-workflow.md)。本文件不扩大用户授权，也不覆盖当前工具或上层规则。

## 1. 默认工作方式

默认由当前主 Agent 保持用户选择的模型和思考强度，完成规划、批准后的实施、基于真实 Diff 的审查和必要验证。已获执行授权后完成整个批准范围，不在第一版实现后无故停止。

执行者、审查方式和文件隔离分别决定，不按风险等级机械创建两个或三个独立会话。普通规划不要求用户额外选择 A/B/C，也不要求重复批准协作阶段。

规划涉及协作时，明确以下三项及其原因，与功能方案一并确认：

| 项目 | 规划内容 |
| --- | --- |
| 执行 | 当前主 Agent，或明确的子任务、执行模型、思考强度和备用执行者 |
| 审查 | 主 Agent 审查，或独立审查的范围、模型和思考强度 |
| 环境 | 统一 QA，或需要额外隔离的目录与原因 |

模型配置核验、单一写入者和有效验证证据是必要约束；侧边栏任务数量不是质量门槛。

## 2. 何时分发

默认不分发。只有同时满足以下条件，才在规划中建议 Luna 实施子任务：

1. 输入、输出和验收标准明确，不需要子 Agent 重新做核心设计。
2. 允许范围可以独立划定，不与另一写入者争用文件。
3. 主 Agent 能通过真实 Diff 和针对性证据验收，不需要逐步指导。
4. 交接成本明显小于预计实施工作量。
5. 子任务运行时，主 Agent 还有验收准备、独立证据核查等有用工作可做。

不满足时由主 Agent 实施。复杂存档、事务、初始化顺序和跨系统状态的核心设计由主 Agent 主导；确定后的数据补齐、引用一致性检查等外围工作可以单独评估。不得仅因任务代码量大就整体交给低成本模型，也不得为了满足并行条件重复实现或重复审查同一工作。

本规范允许按已批准协作方案创建有独立价值的子 Agent，不要求主动分发每个任务。子 Agent 不继续递归分发，除非用户批准的方案明确包含该安排。

独立侧边栏任务只在用户明确要求新建任务，或明确批准其作为长期独立工作时创建。模型不同、Review 需要独立上下文或需要 Worktree，本身都不是创建独立任务的充分理由。

## 3. 模型配置与核验

### 3.1 配置约定

| 角色 | 配置 |
| --- | --- |
| 主 Agent | 保持用户当前模型与思考强度，不自行切换；若为 Luna，同样受 max 约束，配置不匹配按第 3.2 节处理 |
| Luna 子 Agent 或 Luna 独立任务 | 必须显式设置 `gpt-5.6-luna / max`，不允许任何其他思考强度，不得静默降档 |
| 独立审查者 | 默认与主 Agent 使用相同模型和思考强度；如果模型是 Luna，仍必须使用 max。不同配置在规划中单独说明 |

如果认为 Luna/max 的成本或能力不适合任务，改为建议主 Agent 直接实施，不能把 Luna 改为其他强度。用户明确指定的模型与预算边界持续有效。

### 3.2 创建与回显

- 指定模型的创建调用必须同时显式传入模型与思考强度。使用当前工具实际支持的参数，不把角色标题、提示词、自报身份或分支名当作运行配置。
- 如当前子 Agent 接口不允许“完整历史继承”和“模型覆盖”同时使用，选择不继承或部分继承历史并提供精简契约；不能为了继承历史省略模型参数。
- 分别记录请求配置和运行元数据确认的配置。工具接受显式请求但没有返回运行配置时，记录“请求已接受，运行配置未核实”，可以继续，不能声称实际配置已经确认。
- 通过可用工具返回值或运行元数据核实配置；不反复问子 Agent “你是什么模型”，不为缺少回显持续等待或反复扫描日志。
- 工具拒绝配置、必需参数未正确设置，或运行元数据明确不匹配时，阻止该执行者继续写入。若任务已经启动，先停止其写入并核对当前差异。
- 已批准备用执行者时按备用方案继续；否则请求用户决定。Luna/max 不可用时也适用此规则，禁止降档替代。
- 配置记录与实际工作目录、基线、允许范围一起核对。缺少模型回显不等于缺少文件授权，反之亦然。

## 4. 上下文与协调

子 Agent 默认只接收目标、相关规范路径、允许范围、禁止事项、验收标准和基线。需要的源码和资产按路径读取，不复制整个 Session 对话或所有历史日志。

首次交付只提供修改位置或提交、行为变化、验证证据、偏差和未解决问题。返工仅报告相对上次交付的变化；主 Agent 按需查看证据，避免全文转发中间日志。多个 Agent 的 Token 总量不会因使用子 Agent 自动消失，不宣称未经测量的额度节省。

主 Agent 持有子 Agent 或独立任务的真实 ID，负责收取结果并完成后续工作：

- 运行期间做独立工作，不逐段重复审查未完成代码，也不启动竞争写入者。
- 使用完成事件、子 Agent 等待工具或带游标的任务状态工具。等待按当前工具与上层要求分段，不能高频反复读取相同日志。
- 状态显示异常时做一次针对性核查；没有新的异常证据时不持续扫描历史记录，不因摘要未更新认定执行已停止。
- 完成后接回交付包；一般实施错误按批准范围修复，只有需要用户决策的阻塞才询问。
- 用户消息中断等待后，先处理新消息再继续原任务，除非用户取消或明确暂停。
- 不仅确认启动就结束协调回合，也不承诺在没有相应机制时后台持续监控。

## 5. 审查范围与准入

### 5.1 独立审查触发

以下契约变化在规划中默认安排独立审查，与方案一起批准：

- 存档格式、迁移或账号金币等事务一致性。
- 跨世界状态所有权、共享对象池生命周期。
- 全局碰撞矩阵或影响多个系统的 ProjectSettings。
- 多场景或共享 Prefab 的架构变更。

用户明确要求独立审查时纳入方案。单纯 UI 文案、某个 Prefab 数值或普通数据资产修改，不因文件类型自动触发独立审查。意外发现未批准的契约变化，按协作规范确认范围，而不是只给任务换一个风险标签。

### 5.2 审查执行

独立审查使用新的上下文，默认不继承实现过程的完整对话。提供需求、基线、固定被审版本和验证证据；执行总结只是索引，不预设审查结论。

- 主 Agent 实施且未安排独立审查时，依据真实 Diff 自审。
- 子 Agent 实施且未安排独立审查时，主 Agent 对批准范围审查。
- 已安排独立审查时，首次检查批准范围完整 Diff 与相关代码/资产；主 Agent 确认结论、证据和集成边界，不再重复同范围完整审查。
- 后续复审检查上一已审版本到新版本的增量及相关影响，确认原 Finding 闭合并检查回归。
- 读取固定提交的内容；不可把持续变化的工作区当作已经冻结的被审版本。默认只读，不直接修复；需要运行验证时按 QA 单写入者规则安排。
- 是否重跑测试由协作规范的证据要求决定，不因审查者独立就默认重跑完整测试。

准入依据是批准需求、真实 Diff、测试证据和必要偏差说明。P0/P1、实际生产缺陷、资产损坏及关键验收要求缺失阻断交付；非必要测试建议、命名偏好和未来扩展不阻断。必要测试证据缺失不能降为普通建议。每个 Finding 说明触发条件、影响、位置和最小修复方向，不只给优先级标签。

结论使用 APPROVED、CHANGES_REQUESTED 或 BLOCKED_BY_DECISION，并给出被审版本与验证边界。人工尚未确认的视觉、手感等明确列为待验，不冒称通过。

## 6. 返工止损与接管

子执行者负责的同一缺陷经过一次明确反馈和一次修复提交（或固定版本交付）后仍未解决，由主 Agent 接管该缺陷。协作规划预先说明主 Agent 为备用执行者；若用户批准的模型或预算限制不允许接管，先请求决定。

接管步骤：

1. 停止原执行者写入并确认停止完成，不让两个 Agent 同时修同一工作区。
2. 核对当前文件、Diff、分支和已完成证据，保留有效工作，不重置用户修改。
3. 主 Agent 在原批准范围内修复；需要扩大功能或突破硬性限制时另行确认。
4. 对受影响部分验证并增量复审；原独立审查者仍保持只读独立角色。

不自动提高 Luna 强度、不反复新建执行者，也不在每轮复制完整交付报告。Luna 始终只能使用 max。

止损限制的是重复使用无效执行方式，不限制必要缺陷修复次数。用户新增需求更新范围，不计入原任务失败次数。审查通过且证据满足后停止额外润色。

## 7. 统一 QA 与文件隔离

### 7.1 目录职责

- 原始 main 检出：已集成的权威内容、最终集成与归档；未批准功能实现保持在 Session 分支。
- 统一 QA：`C:/Unity_Project/RainsenVampSur-QA`，复用 Unity 导入缓存，用于功能实施、自动化和人工复测。
- Session 分支：`codex/session-X-主题`，保存当前 Session 的可审查改动。
- 当前仓库已批准的纯规范文档修改按协作规范处理，不为文档编辑启动 Unity。

同一 QA 检出同一时刻只允许一名写入者和一个 Unity 实例。子 Agent 共享所在环境的目录，不会自动获得独立 Worktree、不同项目路径或额外写权限。分发前检查实际可访问目录；主 Agent 协调其他工作时不能同时改该检出。

### 7.2 启动与运行

开始新的功能 Session 前：

1. 检查 QA 分支、HEAD、tracked/untracked 状态和已有提交，确认前一 Session 已集成或明确保留。新 Session 从核对过的 main 基线开始。
2. 切分支或执行批处理测试前，确认没有冲突的 Unity/测试进程及有效锁。需要关闭时正常退出，保留未保存工作，不强杀或删除锁绕过占用。
3. 确认 QA 工作区干净后创建或切换批准的 Session 分支，并核对基线；检查 main 是否有会影响集成的未处理改动。
4. 来源不明修改、分叉或活动锁无法安全处理时，停止相关写入并说明原因；不得用 `reset --hard`、强制切换或删除 Library 掩盖状态。

继续同一 Session 或接管返工时，核对当前已知改动及提交，不要求把合法未完成工作清空，也不重做无变化的完整启动流程。保留正常 Unity 缓存；缓存存在不等于旧测试结论有效。用户的 QA 修改须明确归属，不能无记录带入下一 Session。

### 7.3 何时使用额外 Worktree

默认独立上下文审查固定提交，不创建额外检出。仅在以下需要明确时安排 Worktree：

- 需要同时保留不同版本或历史版本复现，且不能扰动当前 QA。
- 需要隔离运行 Unity，现有 QA 无法安全串行复用。
- QA 被其他合法任务占用，或真实独立工作必须并行。

模型选择、任务上下文和文件隔离是三件事。Git Worktree 不能证明模型配置，也不会自动创建侧边栏任务。只有需要移动同一个独立任务的环境时才使用 Handoff。

## 8. 验证、集成与收尾

测试选择、报告适用性、摘要、归档、提交和推送授权统一遵守 [Agent 协作规范](../conventions/agent-workflow.md)第 5、6 节，不另设“每阶段完整门禁”。

普通执行完成后交付实现、必要验证和人工待验说明；没有集成或归档授权时不自动合入 main、写归档或推送。Session 分支本地提交也应属于批准安排。

已有集成或归档授权时，由主 Agent 按统一规则确认准入、处理 fast-forward、核实最终版本测试覆盖并完成相应操作。子 Agent 不自行合入 main、push、归档或停泊 QA。

归档成功后，主 Agent：

1. 确认 Session 提交已集成且推送成功，QA 干净、Unity 正常关闭，无未保存或未跟踪交付文件。
2. 将 QA 切回 `codex/qa` 等专用停泊分支；只有停泊分支无独有提交时才 fast-forward 到已集成版本。
3. 保留 QA 目录和 Unity 缓存；分支无法 fast-forward 时检查原因，不强制覆盖。
4. 临时 Worktree 和短期分支仅在 main 与远端都包含最终提交、且没有未保存工作时才具备清理条件，不做无关清理。

### Session 14

Session 14 在单一 Worktree 中完成实现、反馈修正、自动化和人工复测。该阶段证明短期分支和 fast-forward 可以保持 main 稳定；长期统一 QA 方案在 Session 15 复盘后才正式成为普通串行迭代的推荐环境。

### Session 15

Session 15 同时验证了多任务隔离的价值与成本：

- 首次手动创建 Git Worktree 但没有侧边栏独立 Execute，不能证明使用了指定 Luna 模型。
- 后续真实使用 `gpt-5.6-luna` / `max` Execute 与独立 Sol Review，Review 确实发现了 Prefab 序列化缺陷和测试覆盖不足。
- 正式 Review 共三轮，前两轮为 `CHANGES_REQUESTED`，第三轮 `APPROVED`；第二轮仅恢复一条最大射程测试覆盖，却仍产生完整交接与复审成本。
- 玩家视角的小功能最终触及 25 个文件、对象池、跨世界所有权、ProjectSettings 和 Unity 资产，因此 Plan 必须按真实工程影响而不是标题分级。
- 独立 Review 不是默认必需；轻量走 A、中量走 B、重量走 C，最终由老大选择。
- 长报告、重复完整门禁和多任务上下文重建会抵消便宜执行模型的额度优势；返工后应优先增量复审。
- 普通串行 Session 复用统一 QA 检出，只有高风险独立审查和并行任务使用临时 Worktree。

永久结论：任务流服务于风险控制，不能让流程成本超过功能本身。

### Session 16

Session 16 在统一 QA 检出中执行一个受控的物理契约修正：玩家正式受击 Collider 通过同对象的
`PlayerHurtbox` 显式标记识别，替代“Player Layer 上的非 Trigger Collider”隐式约定。

- `DamageTargetFilter` 仍先按 Player Layer 过滤，再通过 `attachedRigidbody` 解析根节点的
  `IDamageable`；未标记的 `MagnetRadius` 等辅助 Trigger 必须被拒绝，带标记的正式 Trigger
  允许进入同一解析链路。
- `EnemyProjectile` 不再自行拒绝全部 Player Trigger，Trigger 是否为正式受击框完全交给显式过滤器。
- 本次 Execute 继续使用长期 `RainsenVampSur-QA` Local 检出和 `codex/session-16-qa-hurtbox`
  短期分支；不新增 Layer，不修改全局物理设置、玩家数值、对象池、武器、账号、波次或 Session
  归档文件。
- Plan 在 Execute 启动门禁后过早结束，导致完成状态最初需要老大提醒；现已把“持有真实任务 ID、持续等待并自动接回最终交付”写入路线 B/C 的固定步骤。
- 验证必须同时覆盖正式身体、无标记 Collider/Trigger、标记子级 Trigger 的根节点生命解析、近战接触、
  远程弹体穿过 MagnetRadius 后命中正式身体，以及 MainLevel 场景组件绑定；Execute 只提交当前短期
  分支，不合入 main、不 push、不停泊 QA。
