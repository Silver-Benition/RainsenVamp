# RainsenVamp 项目工程规范

> 本文件记录 RainsenVamp 当前及后续开发应遵守的 Unity/C# 工程约定。它描述工程边界，不替代具体功能的设计方案。

## 1. 项目基线

- 引擎：Unity 2022.3 LTS。
- 项目类型：Unity 2D Core 模板。
- 游戏类型：像素风 Survivor-like。
- 视角：近似侧轴横版的 Top-Down 2D。
- 核心约束：海量同屏敌人、自动攻击、经验拾取、武器升级和数值叠加。
- 核心创新：局内动态无缝切换地图，并同步改变环境、敌人池与机制。
- 美术基准：32x32 或 48x48 像素素材，优先保证像素清晰度和逐帧动画表现。

新增功能必须优先检查是否会破坏上述性能目标、像素渲染约束和地图动态切换方向。

## 2. 目录职责

### 2.1 Unity 运行时代码

- `Assets/Scripts/Core/`：全局基础设施和跨系统调度，例如对象池、波次管理和通用管理器。
- `Assets/Scripts/Data/`：ScriptableObject 数据定义和配置结构。
- `Assets/Scripts/Player/`：玩家输入、移动、属性、磁吸和瞄准逻辑。
- `Assets/Scripts/Enemy/`：敌人运行时逻辑、生命、移动、受击和死亡流程。
- `Assets/Scripts/Weapon/`：武器发射器、子弹、光环和武器运行时行为。
- `Assets/Scripts/UI/`：可复用 UI 表现和 UI 数据绑定逻辑。
- `Assets/Scripts/VFX/`：闪白、伤害飘字和其他表现组件。

现有位于 `Assets/Scripts/` 根目录的脚本暂不因为目录理想化而强制移动。新文件应放入职责对应的子目录，文件迁移必须作为单独任务明确确认。

### 2.2 Unity 资产

- `Assets/Data/`：运行时数据资产。
- `Assets/Prefab/`：可复用 Prefab，尤其是对象池预制体。
- `Assets/Scenes/`：场景文件。
- `Assets/Art/`、`Assets/Material/`、`Assets/Shaders/`、`Assets/Sound/`：对应表现资源。

目录职责不能代替组件职责。表现资源可以挂载在运行时 Prefab 上，但伤害、升级和生成规则不能依赖具体美术对象才能成立。

## 3. 架构边界

项目采用数据层、运行时逻辑层和表现层分离的方向：

```text
ScriptableObject 数据
        ↓ 初始化/快照
运行时系统与实体逻辑
        ↓ 事件、接口或表现请求
动画、特效、UI、音效
```

- 数据层负责可配置内容，不保存本局运行时状态。
- 运行时层负责生命、伤害、移动、升级、生成和对象池生命周期。
- 表现层负责动画、闪白、飘字、粒子、音效和 UI，不直接决定核心数值结果。
- 攻击方与受击方优先通过 `IDamageable` 等接口交互，不直接依赖具体敌人类。
- 可池化实体通过 `IPoolable` 或等价的池生命周期接口完成初始化、启用和回收清理。
- 武器初始配置来自 `WeaponDataSO` 等数据资产；攻击时应使用当前等级配置的运行时快照，避免运行中直接污染共享资产。

新增系统必须说明自己属于哪一层，以及通过什么接口或事件跨层通信。

## 4. 性能与生命周期

- 敌人、子弹、经验球、伤害飘字和高频 VFX 等频繁生成对象必须优先使用对象池。
- 战斗热路径中禁止反复 `Instantiate`、`Destroy`、无必要的 `GetComponent` 和临时集合分配。
- `Update`、物理回调和大规模遍历中不得默认使用 LINQ、字符串拼接或隐式装箱。
- 能在 `Awake`、初始化或池取出时缓存的组件引用，不应在每次命中或每帧重新查找。
- 对象从池中取出时必须重置上一次生命周期留下的状态；回收到池中时必须清理目标列表、计时器、速度、事件订阅和表现状态。
- 对象池预制体必须是 Project 资产，不应把场景临时实例当作池模板。
- 碰撞检测优先通过 Layer Collision Matrix、合适的 Collider 配置和低开销的物理回调过滤无关交互。
- 任何“为了修复逻辑而每帧扫描所有实体”的方案，都必须先说明复杂度和同屏规模下的成本。

性能优化不能以牺牲逻辑正确性为代价。应先明确热路径，再决定是否引入缓存、批处理、空间筛选或进一步的数据导向结构。

## 5. C# 与 Unity 编码约定

- 类型、方法、属性和枚举使用 PascalCase。
- 私有字段使用 `_camelCase`；需要在 Inspector 配置的字段优先使用 `[SerializeField] private`，而不是直接暴露为 public 字段。
- 对外暴露只读状态时优先使用属性或只读接口，避免外部随意修改运行时内部状态。
- Unity 生命周期函数保持职责单一；初始化、运行时更新、池启用和池回收应明确区分。
- 复杂逻辑必须添加详尽中文注释，重点解释设计原因、生命周期顺序、Unity API 行为、边界条件和性能考虑。
- 注释不需要逐行解释显而易见的赋值；应帮助处于代码复健期的开发者理解“为什么这样做”和“这一步如何与其他系统协作”。
- 生产代码禁止用模糊伪代码代替关键逻辑。对不确定的 Unity API 版本行为，应明确标注需要查阅官方文档。
- 新增公共 API 必须说明参数、生命周期、调用前提和失败行为。

## 6. 数据驱动与本地化

- 可由策划调整的数值、等级曲线、武器特征、敌人参数和波次规则优先放入 ScriptableObject。
- 运行时变化必须存放在运行时对象或运行时状态中，不能直接修改项目中的共享配置资产。
- 稳定 ID 用于系统识别，不能使用本地化显示名称作为字典键、存档键或逻辑判断条件。
- UI 文本、升级描述和提示信息应预留本地化键值或可替换接口，避免把大段不可替换文本散落在核心逻辑中。
- 数据资产字段的新增、删除和重命名必须考虑已有资产的序列化兼容性，并在执行方案中说明影响。

## 7. Prefab、场景与表现

- Prefab 上的组件依赖必须清晰，必要依赖应在初始化时校验并给出明确错误信息。
- 逻辑判定组件和表现组件尽量分离；例如伤害结果由逻辑层决定，闪白和飘字只负责表现结果。
- Sprite、Animator、Pixel Perfect Camera、Cinemachine 等配置变更必须说明其对像素清晰度、镜头抖动和动画切换的影响。
- 需要对象池管理的 Prefab 必须提供完整的取出、初始化、使用、回收和状态重置路径。
- 新增 Layer、Tag、Sorting Layer 或碰撞矩阵规则时，必须同时说明它与现有交互的关系，避免无意改变全局物理行为。

## 8. 文档与版本控制

- `DevLog/progress/`、`DevLog/code-changes/` 和 `DevLog/retrospectives/` 是历史记录，不是未经核对的实时状态数据库。
- 只有在雨弦明确要求 `/save`、总结进度或把文档更新纳入批准范围时，才更新 DevLog。
- 当前项目以 Plastic 为主要版本控制来源；未经明确要求，不执行 Checkin、Git 提交或远程同步。
- 文档中必须区分“已实现”“已设计但未实现”和“建议 Todo”。
- 跨模型任务优先使用 `DevLog/conventions/agent-workflow.md` 中的交接格式；长期任务可在获得授权后使用 `DevLog/plans/` 保存计划。
