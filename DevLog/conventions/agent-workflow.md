# Agent 协作与双阶段开发规范

> 本文件是项目级、模型无关的协作规范。无论由哪个模型负责规划或执行，都必须遵守同一套流程。

## 1. 适用范围与规则优先级

本文件约束 Agent 在本项目中的读取、规划、写入和交接行为，不覆盖系统级规则、开发者级规则或雨弦在当前对话中的明确指令。

在不违反更高优先级规则的前提下，项目内规则按以下顺序解释：

1. 雨弦当前明确提出的要求。
2. 本文件中的 Agent 协作流程。
3. `DevLog/conventions/project-engineering.md` 中的工程规范。
4. `CLAUDE.md` 与 `.cursorrules` 中的入口规则。
5. `DevLog/progress/`、`DevLog/code-changes/` 和 `DevLog/retrospectives/` 中的历史记录。

历史日志用于了解背景，不自动等同于当前实现状态。当前源码、Unity 资产和本次明确确认的方案才是执行依据。

## 2. 规划模型与执行模型

“规划模型”和“执行模型”是工作阶段，而不是具体模型名称。可以由同一个模型连续完成，也可以由不同模型分别完成。

任何模型在接手任务后，都必须重新读取本文件和相关工程规范，不能假设自己继承了前一个模型的隐式记忆。

### 2.1 规划阶段

规划阶段的目标是理解问题并形成可执行方案，不得产生项目文件变更。

规划阶段允许：

- 读取文件和目录。
- 使用 Glob、Grep 等方式搜索源码和资源。
- 分析当前架构、依赖关系和潜在风险。
- 设计数据结构、组件关系、Unity API 调用和测试方案。
- 输出必要的接口签名、流程图或小段示例代码用于说明方案。

规划阶段禁止：

- 使用 `apply_patch`、Write 或其他方式写入文件。
- 修改 C#、场景、Prefab、ScriptableObject、配置文件或文档。
- 执行会改变项目状态的格式化、资产导入、自动修复或生成操作。
- 将“建议方案”误报为“已经完成”。

规划结果必须明确区分“当前已存在”“本次拟修改”和“未来可选扩展”。

### 2.2 规划输出格式

涉及实际开发的规划，至少应包含以下内容：

```text
任务编号：
任务目标：
当前状态：
需求边界：
架构与逻辑流程：
涉及文件：
允许修改的范围：
明确不修改的范围：
Unity API、组件与设计模式：
验收标准：
验证与测试方案：
风险、假设与未决问题：
```

如果任务可能由不同模型接力，还必须补充一份“执行交接摘要”，使执行模型能够只依赖这份摘要和项目文件完成工作。

### 2.3 执行确认门槛

规划完成后，必须等待雨弦明确确认，才能从规划阶段进入执行阶段。

以下表达可视为明确授权：

- “确认执行”。
- “认同，开始执行”。
- “按这个方案写入文件”。

仅表示理解、继续讨论、提出补充意见或询问细节，不视为写入授权。若雨弦补充了会改变文件范围、架构或验收标准的新要求，必须先更新规划并重新确认。

### 2.4 执行阶段

执行模型只能修改已经获得批准的文件和范围。

执行前必须：

- 重新读取相关规范和目标文件。
- 检查工作区是否存在与任务直接相关的外部修改。
- 对计划中的文件、方法和资源依赖进行一次范围核对。

执行中必须：

- 优先采用最小正确改动。
- 不顺手重构无关代码。
- 不擅自新增兼容层、备用实现或未批准的功能。
- 发现计划外文件确实不可避免时，暂停并向雨弦说明原因，等待重新确认。

执行后必须报告：

- 实际新增、修改或删除的文件。
- 关键实现点和行为变化。
- 已执行的验证命令或 Unity 验证步骤。
- 未完成项目、错误和残余风险。

除非已包含在批准范围内，执行模型不得自动更新 DevLog、提交 Plastic 或执行其他版本控制操作。

## 3. 跨模型交接协议

规划模型应输出可直接交给执行模型的交接摘要。交接摘要至少包含：

```text
Task ID：唯一且简短的任务标识
状态：PLANNED / APPROVED / IN_PROGRESS / VERIFIED
目标：本次必须解决的问题
现状：已确认的代码和资产状态
批准文件：允许写入的具体路径
禁止范围：明确不能改动的路径或功能
实现顺序：执行模型应遵循的步骤
关键约束：性能、生命周期、兼容性和架构限制
验收标准：可观察、可验证的完成条件
验证方案：编译、运行或静态检查方式
未决问题：执行前必须澄清的事项
```

执行模型接手后，应先复述自己理解的 Task ID、批准文件和验收标准。若发现交接摘要与当前工作区不一致，以当前实际文件为准并暂停确认，不得自行猜测。

对于跨多个会话、需要长期推进或风险较高的任务，交接摘要可以在获得写入授权后落盘到 `DevLog/plans/`。普通小改动不强制创建计划文件，以避免文档成本超过功能本身。

## 4. 验证与状态记录

验证结果必须区分以下状态：

- “已静态检查”：仅完成源码或文档检查。
- “已编译验证”：完成指定编译或 Unity 脚本编译检查。
- “已运行验证”：在 Unity 中实际运行并观察到目标行为。
- “未验证”：当前环境无法完成对应验证。

不能因为文件已经写入，就宣称功能已经在 Unity 中验证通过。

如果验证步骤会生成或修改 `Library`、`Temp`、构建产物、Unity 资产或其他项目状态，必须在执行前明确说明其副作用；超出已确认范围时需要再次询问。

## 5. 存档输出规范

一个完整的开发 Session 默认使用三份同编号文档组成归档闭环：

- `DevLog/progress/session-X.md`：面向项目进度的摘要、机制状态和 Todo。
- `DevLog/code-changes/session-X-changes.md`：面向实现细节的类、方法、资源和配置改动。
- `DevLog/retrospectives/session-X-retro.md`：面向架构决策、工程教训、风险和未决问题的复盘。

非代码专项 Session 也应创建对应的 `code-changes` 文件，并明确写出“本次无代码改动”，避免三类归档缺失。

当雨弦输入 `/save` 或明确要求总结进度时，归档摘要必须包含：

- 本次新增或修改的 C# 类、核心方法和删除的临时类。
- 引入的新机制、设计模式和明确的 MVP 范围。
- Unity 手动搭建/等价配置步骤，包括脚本挂载对象、Inspector 引用、Prefab/Scene 层级、按键、Layer、Collider 和其他关键组件设置。
- 已执行的静态检查、编译验证、运行验证和未验证项目。
- 推荐的下一步 Todo List，并区分 MVP 回归、工程完善和长期扩展。

如果 Unity 配置是由 Agent 直接修改 `.unity`、`.prefab`、`.asset` 或 `.meta` 文件完成，也必须记录其等价的手动搭建流程，帮助处于代码复健期的开发者复盘完整链路。
