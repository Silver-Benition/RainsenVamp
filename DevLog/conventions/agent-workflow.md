# Agent 协作、授权与验证规范

> 本文件是项目级、模型无关的协作规则。任务分发与 QA 操作细节见 [Session 工作流](../plans/session-agent-qa-workflow.md)。

## 1. 适用范围与优先级

本文件不覆盖系统级、开发者级规则或雨弦当前明确指令。在上层规则允许的范围内，按以下顺序解释项目规则：

1. 雨弦当前明确要求和本任务已批准的边界。
2. 本文件中的授权、验证和版本控制规则。
3. Session 工作流中的分发、审查与 QA 操作。
4. [工程规范](project-engineering.md)及 `AGENTS.md`、`CLAUDE.md`、`.cursorrules` 入口。
5. 历史 DevLog。

历史日志仅提供背景；当前源码、Unity 资产、工作区和明确批准的方案才是执行依据。入口保持同步，流程细节在本文件维护，避免多处完整复制后相互冲突。

## 2. 按需理解与规划

首次接手任务读取适用的本规范；涉及代码或 Unity 资产时读取相关工程规范。当前上下文已读且未变化的规范可以复用；新接手且没有这些上下文的 Agent 需要读取。执行前核对目标文件最新状态，不因从 Plan 转入 Execute 而重复全面读档。

从目标文件及其直接依赖展开调查。只有背景不足时才查相关历史 DevLog，不强制阅读上一 Session 三份归档或建立全项目地图。

规划阶段允许读取、搜索、分析和展示必要示例；不得写项目文件、导入资产、运行自动修复或其他改变项目状态的操作。

- 小改动说明目标、修改范围、验证方式即可。
- 新增系统、公共契约或跨模块变更，补充当前状态、架构与依赖、Unity API/组件、风险及验收标准。
- 区分当前已存在、本次拟修改和未来可选扩展；仅在图示有助理解时画图。
- 不要求固定 A/B/C 选择或长表单。需要协作时明确执行者、审查范围、环境和备用执行方式，并随功能方案一起批准。
- 普通小任务不创建计划文件；长期任务需要落盘时，将计划文件纳入写入授权。

## 3. 执行授权与范围

### 3.1 一次明确授权覆盖完整实施

规划后获得“确认执行”“开始执行”“按方案写入”等明确授权才写入文件。“认可建议”“继续分析”、询问细节和讨论中的补充不自动授权实施。已经获得的授权在本任务范围内持续有效，不要求重复确认。

执行授权包含批准范围内的实现、必要验证、相关缺陷修复及受影响测试重跑。完成这些工作后再交付，不在第一版实现后无故停下。批准范围内的常规实现方式选择不需要额外确认。

### 3.2 预计文件与硬性限制

| 声明 | 含义 |
| --- | --- |
| 预计修改文件 | 对实现位置的估计；批准模块内为达成同一验收目标所需的辅助类、测试和资源可补充，交付时说明 |
| 硬性限制，如“只允许这三个文件” | 明确白名单或禁止范围；清单外写入需先确认，不得用辅助文件名义绕过 |

规划应明确允许的模块或目录，不能把“预计文件”解释为可写整个仓库。禁止顺手重构无关模块、扩大功能或新增未经批准的兼容层。

只有下列情况需要再次确认相关部分；可以继续不受影响的已授权工作：

- 改变已批准的玩家规则、数值、交互语义或验收目标。
- 突破明确文件白名单、禁止范围或预算限制。
- 引入未批准的存档迁移、公共契约、数据所有权或总体 Scene/Prefab 架构变化。
- 新增未批准的外部依赖或扩大模型预算。
- 无法安全区分或保留用户已有修改，或基线出现无法解释的变化。
- 原验收标准无法达成，需要用户作取舍。

用户提出新要求时更新范围；若消息同时明确授权该变更，不重复索要相同授权。仅提出需求但尚未授权时，先展示修订方案。

### 3.3 验证副作用

批准的验证包含常规 `Library`、`Temp`、日志、报告和构建产物。说明必要影响，不因这些产物单独暂停。

正式 Scene、Prefab、数据资产或配置的变化不能仅因由测试生成就自动获得授权。仅清理由本次操作明确产生的无关污染，保留来源不明和用户修改；不能用强制清理掩盖错误。

## 4. 交接与交付

只有实际分发或跨 Agent 接手时才制作交接摘要，不为同一 Agent 的阶段切换复制完整背景。交接提供目标、相关规范路径、允许范围、禁止事项、验收标准和基线；模型、环境及接管要求按 Session 工作流执行。

交付提供修改位置或提交、行为变化、验证证据、偏差及未解决问题。返工只报告变化部分，原有依据通过文件或提交引用。报告是审查索引，不替代真实 Diff 和证据。

完成条件：批准要求满足、必要验证有效、没有阻断缺陷，并清楚说明人工待验项。不因命名偏好、未来扩展或非必要测试建议持续润色。没有归档或集成授权时，交付后不自动进入对应操作。

## 5. 按变化选择验证

使用 `Tools/Run-ProjectChecks.ps1` 的适用筛选和平台参数执行测试；不因 Plan、Execute、Review、集成等阶段名称而重复运行。

| 修改类型 | 必要验证 |
| --- | --- |
| 纯文档、注释且不改变编译行为 | Diff、链接、规则一致性等静态检查，不启动 Unity |
| 单模块纯逻辑 | 相关 EditMode；影响运行流程时补充相关 PlayMode |
| Scene、UI、对象池、输入或游戏流程 | 相关 EditMode 与 PlayMode；视觉和手感保留人工验收 |
| 存档/事务、跨世界所有权、共享生命周期、全局物理等高风险契约变化，或跨系统改动 | 完整 EditMode 与 PlayMode |
| 正式归档含游戏代码或资产变化 | 有覆盖最终版本的本 Session 完整测试证据；满足下述条件时可使用已有报告 |

完整测试使用 `Tools/Run-ProjectChecks.ps1 -TestPlatform All -NoGraphics`，需要图形环境验证的行为另行覆盖，不把无图形测试当视觉验收。

### 5.1 报告与重跑

已有完整报告可用于本次归档，必须同时满足：

- 来自本 Session，可对应实际被测提交或内容版本。
- 报告后相关代码、资产、包、引擎版本和设置未改变。
- 集成没有产生新的运行内容或合并修复，验证环境没有影响结论的差异。

满足条件的 fast-forward 集成只核对版本和内容对应关系。注明报告来自 QA，不冒称 main 重新运行。只有文档变化也应说明与被测版本的差异。

新改动、失败或未解决疑点出现后，运行受影响测试；高风险变化运行完整测试。无法确定差异影响，或无法确认已有报告覆盖最终版本时，执行完整测试。不设置会阻止必要修复验证的固定次数上限，也不对同一已验证内容无条件重跑。

### 5.2 证据与验收状态

测试失败、编译错误、关键报告缺失、必要测试总数为零或必要用例被跳过时，不得判为验证通过。修复后重跑，或明确标记未验证及原因。

交付区分：

- 已静态检查：只完成源码、资产文本或文档检查。
- 已编译验证：有实际编译成功证据。
- 已运行验证：有实际测试或运行证据；记录命令、平台、数量、失败/跳过情况、被测版本与报告路径。
- 未验证：环境或其他条件不允许完成，说明范围；不适用项可标为不适用。

自动化只覆盖可重复逻辑和流程。视觉、手感、音效、真实设备性能及最终美术由人工确认；人工待验时可以交付待验版本，但不得宣称人工验收已完成。集成前满足批准的人工门槛，或由用户明确接受相应限制。

## 6. 摘要、归档与版本控制

本节统一维护版本控制授权和操作规则；其他入口及工作流引用本节。

### 6.1 指令语义

| 用户指令 | 行为 |
| --- | --- |
| 仅补充资料，没有提出任务 | 回复“项目状态已同步，当前进度清晰，请老大指示下一步开发任务。” |
| 补充资料并提出具体任务 | 同步后继续处理任务 |
| `/save` 或“总结本次进度” | 仅在回复中输出开发摘要，不写 DevLog、不 commit、不 push |
| “归档”或“执行归档流程” | 写三份同编号 DevLog，并按本节提交、推送和验证远端 |
| “只更新 DevLog，不提交”等具体限制 | 遵守明确限制，不自动补做被排除的步骤 |

开发摘要包含本次新增/修改的 C# 类和核心方法、机制或模式、Unity 手动搭建或等价配置、验证状态和下一步 Todo；没有对应变化时简要注明，不编造内容。

### 6.2 正式归档

完整开发 Session 使用三份同编号文档：

- `DevLog/progress/session-X.md`：进度、机制状态和 Todo。
- `DevLog/code-changes/session-X-changes.md`：类、方法、资源及配置变更。
- `DevLog/retrospectives/session-X-retro.md`：决策、教训、风险和未决项。

正式归档的非代码 Session 也保留三份文档，并写明无代码改动；普通聊天摘要不创建它们。Agent 直接修改 Unity 资产时，记录等价手动配置，包括挂载、Inspector 引用、层级、按键、Layer 和 Collider，帮助复盘。

### 6.3 Git 与集成边界

- Git `main` 是已集成的权威分支；批准前的功能实现放在 Session 短期分支。当前仓库已获批准的纯规范文档修改可按任务范围直接进行，不为其建立 Unity QA 环境。
- 规划明确短期分支及提交安排后，执行授权可包含 Session 分支上的本地提交；否则不把文件编辑授权当作自动提交授权。只有获得集成或归档授权才合入 main。
- 每次 Git commit 的提交信息必须包含 `session-X`。Session 编号依据本任务确认的信息，不为提交随意编造编号。
- “归档”默认授权主 Agent 检查、提交本 Session 改动并推送 origin 当前交付分支；标准 QA 流程在准入通过后 fast-forward 集成到 main，再推送 origin main。用户指定其他分支时遵守该要求。
- 集成准入：审查通过、必要验证和人工门槛满足、main 无未处理改动，执行提交是 main 的可验证后继。不可 fast-forward 时不得强制覆盖，先明确分叉原因和处理方案。
- 按第 5 节核实最终版本的测试覆盖，不强制集成后再跑相同内容。归档文档、提交范围与实现及证据一致。
- 只纳入本 Session 的文档、代码、场景、测试和新增资源。保留无关或来源不明修改；不能安全区分时请求明确范围。
- 仅执行普通 commit 和 push，不 force push、不重写历史、不破坏性清理。不得自行执行其他版本控制系统的 Checkin。
- 推送后核对本地提交与远端目标分支；失败时报告具体原因和“已提交但未上传”等真实状态，不宣称上传成功。
- 子 Agent 不自行合入 main、push 或归档；主 Agent 按本节完成最终集成和同步。QA 停泊及临时检出清理条件见 Session 工作流。
