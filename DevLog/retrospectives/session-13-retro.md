# Session 13 复盘：属性公式通过不代表交互语义完成

- 日期：2026-08-28
- 主题：角色属性阶段二、对象池物理边界、可选复活与一次升级机会的定义。

## 本次最重要的架构决策

### 单局次数和统计必须有唯一权威来源

击杀、金币和 Revival/Reroll/Skip/Banish 如果分别由 UI 或各自管理器维护，会在重开、订阅顺序和属性重算时产生副本分歧。RunState 因此成为单局权威状态，UI 只订阅，功能系统只请求消费。

次数属性采用“容量差额”同步：从 2 增长到 3 时只增加一个剩余次数；同一属性来源重复重算不会返还已经使用的次数。这一规则可以直接复用于阶段三被动和永久进度加成。

### 出生快照隔离共享数据和对象池生命周期

Curse、Charm、Defang 属于生成瞬间规则。EnemySpawnSnapshot 把共享 EnemyDataSO 与单个实例运行时状态分开，避免：

- 修改玩家属性后反向改变全部在场敌人。
- 池化实例继承上一生命周期的伤害、速度或颜色。
- 远程投射物在来源敌人回池后读取错误状态。

敌方飞行道具在发射时复制最终伤害，不长期持有来源状态。这一点对未来远程敌人和弹幕池十分重要。

## 人工测试发现的三个关键缺口

### Defang 的逻辑值正确，池化物理边界仍可能伤害玩家

最初自动化只验证绿色快照的接触伤害和远程伤害为零，以及下一次取出恢复基础状态。老大在真实包围场景发现极低概率扣血。

根因位于回池边界：OnDisable 原先立即恢复基础伤害，而 Unity 可能在同一物理步内继续派发已经排队的碰撞消息。修复采用双保险：

1. 回池后的 EnemyBase 使用零移动、零输出安全快照。
2. OnCollisionStay2D 同时拒绝 `!isActiveAndEnabled`、Defang 和非正伤害。

新增真实 Physics2D 持续碰撞并在接触中停用敌人的 PlayMode 用例，测试从“字段正确”提升到“玩家生命没有变化”。

### Revival 的数值实现正确，但交互假设错误

最初实现把 Revival 解释为“死亡事件发生后自动消费并立刻半血恢复”。老大的预期是死亡仍然具有选择权：先进入正常死亡界面，可以退出或主动复活。

修正后把流程拆成三层：

- PlayerHealth 只负责死亡和恢复生命。
- RunState 只负责是否仍有次数以及确认后的消费。
- GameFlowManager 负责死亡面板、按钮选择、非缩放时间动画和暂停解除。

经验是：资源“存在”不等于资源“自动使用”。涉及玩家重要决策时，验收标准必须描述输入时机和取消路径，不能只描述最终数值。

### Banish 必须定义一次升级机会的所有权

最初 Banish 选择后刷新候选，允许玩家继续领取升级；这等价于免费获得“删除一项内容”的附加操作。老大的规则是放逐和领取升级二选一，因此放逐必须消费整个升级机会。

修复后 Banish 写入稳定 ID 并直接调用 CompleteCurrentChoice。后续候选统一过滤该 ID，但本次不再提供第二次选择。

经验是：Reroll、Skip、Banish 不只是三个按钮，而是对同一“升级机会”状态机的不同终止或转换操作。

## QA 基础设施问题

Windows 上的 Unity 启动器可能先返回，而真实 Editor 进程仍在导入和写入报告。仅等待 XML 文件出现会读取到半成品；全新隔离工程首次导入微软雅黑字体还可能超过一分钟。

Run-ProjectChecks 现在等待 `test-run` 节点可解析，并把首次导入上限调整为五分钟。标准门禁在预热隔离工程中稳定通过 EditMode 48/48、PlayMode 19/19。

## 做得好的地方

- 九项属性没有把规则散落到 UI，而是分别落到候选解析、RunState、波次快照、生命和掉落系统。
- 双世界和旧 WaveManager 使用同一公式，减少不同生成路径的行为漂移。
- 概率和候选算法可注入确定随机源，测试不依赖偶然结果。
- 手工反馈修正后都补入自动化，避免下一阶段重构时恢复旧行为。
- 现有角色仍保持中性值，系统接入没有偷改正式平衡。

## 仍然存在的风险与不足

- 当前没有真实远程敌人；EnemyProjectile 的来源快照已验证，但第一种射手仍需检查发射器是否总是传入 EnemyBase。
- 复活按钮和升级操作栏是运行时构建，逻辑回归稳定，但不同分辨率下的最终视觉仍以人工验收为准。
- 宝箱奖励只有单武器即时升级和临时外观，没有多奖励、开箱演出或稀有度系统。
- RunState 不持久化；阶段三不能直接把它跨场景保存，应建立独立账号进度模型。

## 阶段三交接重点

### 已有可复用底座

- CharacterDataSO、角色选择页和 CharacterSelectionSession。
- PlayerStats 稳定 sourceId 修改器。
- UpgradeDataSO 稳定 upgradeID。
- LevelUpManager 的合法候选集中入口。

### 建议实现顺序

1. 建立版本化账号存档和 AccountProgress 权威服务。
2. 接入角色解锁和选择页锁定状态。
3. 配置并授予角色起始武器。
4. 用第一个正式角色被动验证 PlayerStats 稳定来源链路。
5. 建立收藏页面和发现状态。
6. 最后接入跨局 Seal，并与单局 Banish 保持不同数据域。

### 开始前必须明确的策划项

- 蓝衣战士的正式解锁条件。
- Seal 初始数量、上限与获得方式。
- 收藏页面首版包含角色、武器、升级项，还是同时包含敌人图鉴。
