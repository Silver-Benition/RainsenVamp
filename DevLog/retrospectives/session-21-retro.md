# Session 21 复盘：性能证据可信度与有界诊断

- 日期：2026-09-11
- 范围：主世界高密度验收、宝箱字体修复、短程长帧诊断与归档。
- 结果：约定的主世界受控负载门槛通过；字体引用修复；老大决定结束本轮修复并关闭未复现/未完整捕获的尖峰追查。

## 有效做法

1. 先查实际活动量，再谈性能。普通场景怪物过少不能代表高密度；生成副本沿用正式生成、伤害、死亡与池化链路，避免空对象压力替代真实游戏。
2. 将主世界范围落实到场景序列化状态。副世界在 Awake 前禁用，比进入游戏后再关闭更可靠，且不改正式副世界功能。
3. 压力模式和自然游玩分开。随机宝箱、冻结和升级会污染窗口；受控副本只移除明确干扰项，保留经验、金币、Captain 与真实战斗，结束恢复覆盖。
4. 报告包含失败与缺失。活动数与可见估计分别报告；负载不足、中断、缓冲溢出、计数器异常不能包装成有效结果。GPU 不支持就保留无效状态。
5. ABBA 先检查匹配再比较。四个短窗口只支持“本轮未测得明显额外开销”，不把 +0.027 ms 波动当成采样器确定成本。
6. 字体问题从引用链定位：Toast 需要 TMP_FontAsset，却绑定原始 TTC。修正现有资产引用即可，通过类型/图集/材质与真实文字网格测试防回归，没有扩大为 UI 重写。

## 诊断中学到的边界

阶段报告只描述纳入窗口的帧。阶段末排序、序列化和写盘会造成工具长帧，因此旁路连续记录保留边界工作；本次 CPU 已定位一帧 83.3434 ms 中 80.7256 ms 属于工具报告区段，不能写成游戏战斗瓶颈。

Unity CPU 捕获最初只解析到末尾 300 帧。检查帧范围后，在离线进程扩展历史长度并完整解析 13789 帧；工具成功退出不等于捕获完整，必须同时核对首尾帧和原始文件。

CPU 帧与下一次 Update 观察的帧间隔需要对齐。渲染线程等待不等于 GPU 算力耗时；父子样本不能相加；捕获从一帧中途开始时不能归因整帧。GC 累计次数和内存趋势也不能单独证明长帧原因或不存在泄漏。

原 437.3255 ms 稳态尖峰在四次独立启动、八个满武器窗口中未复现；切换尖峰捕获不完整。2026-09-11 老大明确选择停止诊断，按当前项目决策不再视为待处理问题。归档保留历史事实与关闭决定，不伪造“已修复”的因果结论，也不继续追加无边界采样。

## 交付与证据管理

- 隔离资产和编译成功只是准备阶段，必须有完整门禁及实际图形 Player 的有效负载报告才可交付性能结论。
- QA 最终 EditMode 112/112、PlayMode 47/47；按路线 B 快进 main 后另跑完整集成门禁，报告见同编号进度归档。归档测试不能替代真实设备性能证据。
- 性能报告保留当时 sourceRevision + sourceHash，避免后来 commit 号伪装原始构建身份。
- 大型 CPU raw、Builds 和 Logs 保留本地，不混入 Git 提交；三份受版本管理的归档保存关键结果、条件与原始证据位置。
- 本轮没有新增人工视觉验收记录。已知验证边界记录清楚，按老大收尾决定归档；自动化与日志证据不冒充人工观感通过。

## 下一步

本轮没有必须继续的性能优化。回到正常功能开发，由老大确定下一项需求；宝箱中文显示可在日常游玩时顺带查看。副世界或其他硬件的性能需求以后单独规划，不继承本轮主世界通过结论。
