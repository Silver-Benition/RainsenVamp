# Session 20 复盘：高清不是放大，冻结也不是暂停全局时间

- 日期：2026-09-04
- 基线：`ea17933`
- 实施分支：`main`
- 结论：地图即时拾取物、资源外飘、敌对世界冻结和高清像素显示链已完成；静态画质人工验收通过，高密度性能验收保留为开放待办。

## 架构决策

### 1. 地图即时效果采用“拾取壳 + 无状态策略”

`MapInstantEffectPickup` 只负责触发、消费守卫、统计和回池；治疗与冻结分别由 `MapInstantEffectSO` 子类实现。这样新增效果时不需要继续膨胀一个拾取脚本，也不会把运行时计时写进共享 ScriptableObject。

效果是否成功由 `TryApply` 返回值决定。舰长满血时虽然世界物体会被消费，但不会把“没有恢复任何生命”记录为成功效果，保证结果页统计口径可信。

### 2. 地图道具与资源磁吸必须分开

经验和金币属于高频资源流，磁吸能减少回收成本并改善节奏；舰长和水晶球属于低频强效果，必须要求玩家主动走位接触。因此地图道具完全不实现 `IMagneticPickup`，而不是通过半径或标签做脆弱的运行时特判。

### 3. 磁吸动画从奖励逻辑中抽离

经验与金币原本各自保存目标、速度和逐帧追踪状态，继续增加外飘阶段会复制两份状态机。`MagneticPickupMotion` 把表现统一为 `Idle -> Scatter -> Homing`，奖励脚本回到单一职责。

外飘使用确定性实例哈希而不是 `Random`：既能避免完全重叠时方向为零，也不会让纯表现消耗全局随机序列、改变掉落或战斗结果。

### 4. 冻结使用领域状态，不修改 Time.timeScale

水晶球需要“除了玩家以外的敌对世界冻结”，而不是暂停整局。若修改 `Time.timeScale`，玩家输入、玩家武器、经验金币、HUD 与权威计时都会一起停止，语义错误且容易与升级/暂停/结算原因冲突。

因此 `WorldFreezeController` 只提供统一冻结状态；敌人、Boss、敌方弹体、波次和敌对 VFX 在各自生命周期边界响应。刚体、Animator 和弹体动量都显式保存并恢复，保证对象池复用安全。

### 5. 蓝色蒙版只观察状态，不控制状态

`WorldFreezeOverlay` 订阅 `FreezeStateChanged`，只切换 SpriteRenderer。逻辑层不知道具体颜色、排序或素材，表现层也不能延长冻结时间。玩家与血条使用 Player Sorting Layer 位于蒙版上方，普通世界位于蒙版下方，满足“冻结世界但不染蓝玩家”的视觉语义。

### 6. 高清显示必须同时控制源图、世界尺寸和采样链

最初把素材直接缩成低分辨率会永久丢失细节；只保留高清源图再用极小 Transform Scale，又会造成非整数采样和不稳定的屏幕像素覆盖。

本次最终采用三层约束：

1. 用 PPU 决定高清源图在世界中的物理尺寸，Prefab Scale 保持 1。
2. 使用 Point、无压缩、无 Mipmap和二值 Alpha，避免导入与边缘混色。
3. Pixel Perfect Camera 直接输出目标分辨率并执行 Pixel Snapping，取消低分辨率中间纹理的先压缩后放大。

能力图标则使用 48×48 源图配 96×96 容器，避免原 100×100 带来的 2.083 倍非整数显示。

## 做得好的部分

- Session 19 预留的 `MapInstantEffectPickupDataSO` 与结果统计接口可以直接扩展，没有污染经验、金币或宝箱类型。
- 冻结权威不依赖 `Time.timeScale`，与既有暂停原因、结算冻结和玩家行动保持清晰边界。
- 敌人与弹体都显式恢复池生命周期状态，避免只修正“屏幕上看起来停止”却在复用后留下约束或速度错误。
- 经验与金币共享外飘状态机，减少重复字段、重复 Update 和未来表现分叉。
- 素材清晰度通过原始像素、Importer、Prefab 世界尺寸、相机链路和 UI 容器多层自动化锁定。
- 独立 QA 在 66 个文件哈希一致的前提下通过 101/101 与 44/44，并在测试后恢复干净。

## 本次失误与修正

### 路线 C 曾被错误宣称完成

第一轮只修改了升级图标容器，没有实际替换六枚能力 PNG，却把“显示链优化完成”表述成“路线 C 完成”。这是交付状态不诚实：计划的一部分通过，不能代表整条路线完成。

修正后重新生成并实际覆盖六枚同名 PNG，用文件哈希确认内容变化，并增加二值 Alpha 自动化断言。今后所有素材替换必须同时给出：项目内最终路径、文件哈希变化、Unity 引用保持情况与运行验证，不能只凭生成预览或配置变更宣称落地。

### 不能用预览棋盘格判断透明度

图像生成结果曾出现真实 RGBA、白底 RGB 和“把棋盘格画进图片”三种情况。预览看起来像透明并不构成证据。本次最终以文件像素格式和 Alpha 统计筛选，且把主体 Alpha 离散为 0/255，消除高比例 254 Alpha 对像素边缘的潜在软化。

### 模糊的根因不是单一 Importer 参数

Point Filter 只能避免颜色插值，不能恢复被 480×270 中间画布压掉的细节，也不能修复 48×48 到 100×100 的非整数覆盖。修复必须沿“源图 -> Importer -> PPU/RectTransform -> Camera/Canvas -> 屏幕输出”整条链路检查。

## 性能风险

- 原生分辨率世界渲染会提高 Sprite 片元填充量；当前小规模场景通过运行验证，但不代表目标敌群密度下仍有足够 GPU 余量。
- 蓝色全屏蒙版增加一层透明 Overdraw；单层成本通常可控，但必须与海量透明 Sprite、弹幕和 VFX 一起测量。
- 敌人和弹体当前通过轻量静态布尔状态判断冻结；进入/退出冻结时才执行较重的组件状态切换，但目标规模下的 CPU 峰值仍需 Profiler 验证。
- 高密度性能不过关时，优先处理对象池预热、材质批次、透明区域、查询频率、冻结状态广播和渲染排序；不默认牺牲已经验收通过的高清像素基线。

## 后续原则

1. 新增地图即时效果优先增加新的无状态策略资产，不在通用拾取壳中堆叠类型分支。
2. 新增冻结对象时，明确它属于玩家侧、敌对侧还是中立世界，再决定是否响应冻结权威。
3. 新增像素素材时同时定义源分辨率、PPU、目标世界/UI 尺寸和整数倍率，而不是依赖 Transform 临时缩放。
4. 任何“优化完成”结论都必须对应实际落盘文件与可检查证据；生成草稿、计划或局部配置不能冒充最终交付。
5. 按 `hd-rendering-performance-validation.md` 在内容密度达到条件后执行专项性能验收；若失败，先优化性能，再讨论任何画质取舍。
