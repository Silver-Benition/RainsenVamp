# Session 15 复盘：远程敌人的边界正确性与任务流必须按风险付费

- 日期：2026-08-30
- 主题：远程敌人、敌方弹体、共享对象池的跨世界所有权、Unity 资产序列化、自动化测试语义，以及 Sol/Luna/Worktree 流程成本。

## 本次最重要的架构决策

### 远程敌人应复用 EnemyBase，而不是建立第二套敌人框架

RangedEnemyController 只承担距离带移动和发射周期。生命、移动速度、接触伤害、受击、死亡、掉落、玩家目标和池生命周期继续由 EnemyBase 提供。

这样第一种远程敌人不会复制近战敌人的基础逻辑；未来增加散射、蓄力或预判攻击时，可以扩展攻击数据和控制器，而不改变生命与掉落底座。

### 弹体必须快照伤害和方向

弹体生成时记录发射瞬间方向，不持续追踪玩家。最终伤害通过来源 EnemyBase 解析后写入弹体，因此：

- Defang 敌人发出的弹体固定为 0 伤害。
- 敌人回池或状态变化不会反向改变飞行中的弹体。
- 池复用时只需清空弹体自身快照和速度，不依赖旧来源对象继续存在。

### 隐藏世界不能简单禁用整个 GameObject

项目核心要求世界切换后非当前世界仍继续模拟。如果直接 SetActive(false)，敌人移动、攻击计时和弹体寿命都会冻结。

最终规则为：

- 关闭 Renderer 和 Collider。
- 禁止接触与弹体伤害交互。
- 保留 GameObject 活跃，使移动、攻击周期和寿命继续推进。
- 对象池所有权决定哪个 WorldEnemySimulation 有权切换实例状态。

### 共享对象池必须跟踪“当前所有者”

A 世界回收实例后，B 世界可能立即取出同一个 GameObject。如果 A 仍把它保留在自己的历史集合中，之后 A 的 SetWorldActive 就可能错误关闭 B 正在使用的实例。

WorldEnemySimulation 因此把敌人和弹体归属绑定到当前所有者。旧世界只能处理仍由自己拥有的实例，池复用后不能夺回 Renderer、Collider 和交互状态。

### 玩家 Layer 不能等同于正式受击体

MagnetRadius 等辅助 Trigger 位于玩家层级中。如果弹体只通过父级查找 PlayerHealth，进入磁吸范围就会提前伤害玩家。

当前修复忽略 Player Trigger，只允许正式非 Trigger Collider 成为受击体。这解决了首版问题，但也留下明确边界：未来若正式受击框改为 Trigger，必须引入独立 Layer 或显式受击标识。

## Unity 资源教训

### 运行正常不代表 Prefab 源文件合法

EnemyProjectile_1 的 MonoBehaviour 实体存在，但 GameObject.m_Component 最初没有引用它。Unity 2022.3 在导入时自动修复内存对象，因此正式资源测试仍然通过；干净导入日志却明确报告 Prefab 组件链损坏。

这说明 Unity 资产审查必须同时检查：

- 运行时加载结果。
- Prefab/Scene YAML 的组件引用。
- 干净导入日志中的自动修复警告。
- 测试后是否出现 tracked 重序列化副作用。

### 双帧图片必须检查实际切片，而不只检查 PNG 尺寸

三张敌人源图都是 64×32。如果按 Single Sprite 导入，远程敌人会横向显示两帧。老大的人工复测比纯逻辑测试更早暴露了问题。

修复保留 PNG 像素和 GUID，只改变 `.meta`：两个 32×32 Sprite、32 PPU、Point 过滤。未来建立 Animator 时可以直接复用稳定切片。

## 自动化测试教训

### 测试名称和测试数量不能证明语义覆盖

第一版“首发延迟”测试先让玩家在 20 米外等待 1 秒，0.8 秒计时已经耗尽，再把玩家移入射程。即使生产代码生成后立即准备发射，该测试仍会通过。

强化后改为玩家从生成时就在射程内，并使用真实 ActiveProjectileCount 验证：

- 0.8 秒前没有首发。
- 成功首发后 2 秒内没有第二发。
- 同一敌人回池复用后重新开始首发延迟。

### 修一个覆盖缺口时不能删除相邻覆盖

第一次返工强化首发和冷却测试时，旧用例中的“20 米外不发射”断言被删除。测试总数仍为 26，全部通过，但运行时 MaxRange=8 的保护已经消失。

最终返工在同一活跃敌人生命周期末尾恢复 20 米、等待 2.2 秒仍为零弹体的断言。今后修改测试必须比较修改前后的需求覆盖矩阵，不能只看绿色数量。

### 复杂生命周期值得真实池和双世界夹具

世界隔离不能只通过静态读取代码证明。最终 PlayMode 使用真实 PoolManager、两个 WorldEnemySimulation、两个 WorldWaveManager 和同实例复用，覆盖：

- 非当前世界敌人不可见、无碰撞、无伤害但继续移动。
- 非当前世界弹体继续飞行并消耗 RemainingLifetime。
- A 回池、B 复用后，A 的世界切换不能影响 B。

这类测试成本较高，但它直接保护项目核心的双世界共享池契约。

## Sol/Luna/Worktree 流程实验

### 独立 Review 有价值，但不是免费质量

Session 15 的独立 Sol Review 确实发现了一个真实 Prefab 序列化缺陷，也发现了三个测试语义/覆盖问题。Review 的价值成立。

但正式 Review 共运行三轮，前两轮要求返工，第三轮批准。第二轮只发现一次测试返工删除了最大射程断言；为一个测试文件的小增量继续传递完整交付包、重建上下文和重复全量门禁，成本明显超过修复本身。

### 便宜执行模型可能被交接成本抵消

Luna 适合明确范围内的快速实现，但 Plan、Execute、Review 多任务会重复读取规范、源码、Diff 和测试证据。长交付包、多次切换和完整 Unity 门禁会继续扩大两个任务的上下文。

因此“执行模型更便宜”不自动等于“整条流水线更省额度”。流程必须按任务风险选择，而不是把三任务隔离设为默认。

### 新的 A/B/C 决策门

后续 Plan 必须先输出轻量/中量/重量判断、推荐路线、依据和升级条件，由老大最终选择：

- A：Sol 单任务完成 Plan、Execute、自审、验证与集成。
- B：Sol 负责 Plan/Review/集成，默认 Luna 负责 Execute 和全部返工。
- C：只有重量任务才增加独立 Sol Review 和临时 Worktree。

Execute 默认 Luna/max，但老大可以指定任意可用模型和推理强度。若实际范围超过 Plan 预测，Execute 必须暂停申请升级流程。

### 返工应做增量复审

- 第一次 Review 检查完整基线 Diff。
- 返工后只检查上一已审提交到新提交的增量，并确认没有覆盖回退。
- 测试专用小改动优先运行目标测试，不自动重跑一轮完整独立审查。
- Review 必须区分当前真实缺陷和未来测试债务；不是每个 P2 都必须以同样成本阻断。

## 统一 QA 构筑决策

Codex Worktree 是完整的第二份 Git 检出。每个 Session 都创建新 Worktree 会重复占用 Unity 项目文件、Library 导入、测试报告和许可证初始化成本。

后续普通串行迭代采用一个长期统一 QA 检出：

- main 保持权威和稳定，只做最终集成、归档和 push。
- QA 目录复用 Unity Library/Temp 缓存，在 Session 短期分支上实现和验证。
- 同一时间只允许一个写入任务和一个 Unity 实例使用 QA。
- 每个 Session 开始前检查干净状态、基线、分支和锁；发现不明状态不得强制重置。
- 集成并推送后把 QA 停泊分支 fast-forward 到 main，保留目录供下次使用。
- 只有重量独立 Review、真实并行任务或历史复现才创建临时 Worktree。

统一 QA 解决的是磁盘和导入重复，不取消短期分支、冻结基线、自动化和 Review 边界。

## 环境问题与处理

### CreateProcessWithLogonW 1385

独立 Review 最初无法运行任何 Git 命令，终端在进程创建前返回 `CreateProcessWithLogonW failed: 1385`。该错误只能证明 Codex 沙箱身份缺少本地登录权限，不能证明 Git 或产品状态。

恢复 Windows“允许本地登录”的 BUILTIN\\Users 后，原 Review 任务可以继续完成独立 preflight 和 Unity 门禁。以后遇到同类错误必须停止并标记环境阻塞，不能采用 Execute 自报结果代替独立证据。

### Unity SafeNet 许可证沙箱

main 集成后第一次门禁在沙箱内返回进程码 0，却没有测试 XML，并在项目根生成 SafeNet 日志。随后在宿主权限上下文重新运行同一命令，成功得到 65/65 和 26/26。

缺少 XML、测试总数为零或 Unity 没有生成日志时只能标记“未验证”；清理失败运行的精确临时日志后，必须使用新报告收口。

## 做得好的地方

- 远程敌人复用 EnemyBase，没有复制第二套生命、掉落和池逻辑。
- Defang、固定瞄准、掩体阻挡和 Player 辅助 Trigger 边界均进入自动化。
- 非当前世界继续模拟与共享池所有权得到真实双世界测试。
- 老大人工复测及时发现 Sprite 导入问题。
- 独立 Review 最终确认基线到功能提交只有批准的 25 个文件，三轮后无剩余 Finding。
- main 集成后重新运行全量门禁并保留新鲜报告。
- 流程实验没有被当作固定教条，最终根据额度成本改成风险分级。

## 仍然存在的风险与不足

- Player Trigger 全部忽略是首版规则，不适合未来 Trigger 型正式受击框。
- 远程敌人只有静态首帧，没有独立动画、音效和更丰富攻击表现。
- 远程敌人的战斗节奏和屏幕压迫感仍需要长期人工调参。
- 长期统一 QA 规则已经写入文档，但物理 QA 检出和 Codex 本地项目尚需在下一 Session 前建立。
- 独立 Review 的具体启用阈值仍需在后续 Session 中继续校准。

## 后续 Session 交接重点

1. 每次 Plan 先给出任务重量、A/B/C 推荐、依据和升级条件，等待老大选择。
2. 普通 Session 优先在统一 QA 检出执行；没有必要时不创建临时 Worktree。
3. 远程敌人扩展必须复用 RangedEnemyAttackDataSO、RangedEnemyController、EnemyProjectile 和 WorldEnemySimulation 所有权契约。
4. 修改 Player Collider、WorldEnemySimulation 或对象池时，保留 Session 15 的 6 项 PlayMode 行为覆盖。
5. Unity 资源交付同时检查运行结果、YAML 组件链、干净导入日志和测试后 Git 状态。
