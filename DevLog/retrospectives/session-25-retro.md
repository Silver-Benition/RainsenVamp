- 先用带图标、稳定 ID、数值和处理意见的工作簿批量审阅，再接入游戏，减少逐条聊天对照成本。V1 保留用户意见，V2 保留处理结果和未擅自采用的候选数值。
- 把“是否叠加”“件数上限”“品质”显式存入数据，正负属性使用同一累计路径；商店单件收益与背包累计收益分别展示。
- 糖块和沙漏的运行状态独立于 SO 配置，通过现有生命/回合事件驱动，避免每帧扫描与修改共享资源。

- 线上研究页遭站点安全拦截时保留完整本地网页，使资料访问不依赖登录或托管服务恢复。

## 暴露的问题与教训

1. **无限叠加不能直接驱动 UI 数量。** 新道具 MaxLevel 使用 int.MaxValue，旧 F7 遍历每一级创建按钮，导致数十亿次循环及潜在溢出。已改固定按钮和最多 5 件的有界授予，后续所有消费该上限的 UI 都应检查是否将逻辑上限错误当作可枚举集合。
2. **“配置了效果”不等于“运行时实现了效果”。** 棱晶飞梭 Tracking 分支只是占位；原测试只证明生成/飞行/回收，没有证明命中后转向。当前已明确列为未完成并由用户要求留到下一会话，不用全套测试通过掩盖覆盖空白。
3. **视觉层也可能被旧逻辑读取。** 陨铁锤隐藏根渲染器后，旧离屏回收逻辑读取无效 bounds 导致提前回池。通过最终图形检查发现，并恢复根渲染器和等效碰撞尺寸；后续调整表现层前应核查现有逻辑对 renderer.bounds 的依赖。
4. **编辑器资源加载有顺序依赖。** 导入工具需先打开目标场景再取得目录引用；否则切场景时原引用可能失效。修正后再生成并验证目录与场景引用。
5. **测试环境需匹配验证目标。** EditMode 的生命周期要显式准备；背包滚动内容允许处于遮罩之外，不能要求所有子按钮一直在屏幕内；IMGUI 截图在 batchmode 下不可靠，F7 最终改用有窗口的测试进程获取实际截图。
6. **武器名字与动作不可混同。** “细剑”“长枪”目前只有不同数值、图像和挥击弧度，没有真实刺击；预设完成不能被概括为武器系统已完善。
