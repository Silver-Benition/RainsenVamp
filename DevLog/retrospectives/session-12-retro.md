# Session 12 复盘：角色引用正确不等于运行时属性正确

- 日期：2026-08-27 至 2026-08-28
- 主题：角色选择、统一属性快照、Unity 初始化顺序与真实消费者回归。

## 本次最重要的决策

### 用角色资产描述静态身份，用 PlayerStats 保存本局最终快照

CharacterDataSO 只保存角色稳定 ID、选择页表现和基础属性，不在运行时修改。PlayerStats 在开局读取角色资产，并把角色基础值与能力、装备、调试等来源的修改器聚合为最终快照。

这一边界让角色配置、运行时状态和 UI 展示保持分离：

CharacterDataSO → PlayerStats 最终快照 → 生命/移动/武器/磁吸等消费者 → UI 只读展示。

### 修改器按稳定来源整体替换

同一能力升级时，如果只追加新修改器，旧等级会永久残留并重复叠加。当前用 sourceId 保存每个来源的完整修改器集合，升级时整体替换，卸下时整体移除。

Flat、AdditivePercent、Multiplicative 使用固定计算顺序，既便于策划理解，也方便测试精确约束。

### 角色选择必须在第一次属性读取时生效

最初实现把 CharacterSelectionSession 的消费放在 PlayerStats.Awake 中，隐含假设 PlayerStats.Awake 一定早于所有属性消费者。这个假设在 Unity 中不成立：不同 GameObject、父子层级和组件的 Awake 顺序不应作为业务正确性的前提。

最终将角色解析放入 EnsureStatsInitialized 的最前端。无论 PlayerHealth、PlayerMagnet、武器还是 UI 谁先读取属性，第一次快照都以菜单确认角色为准。

## 本次暴露的缺陷

### 表面状态正确掩盖了缓存错误

蓝衣战士选择页显示正确，进入 MainLevel 后 PlayerStats.CharacterData 也确实指向 BlueWarrior，但最终属性数组已经提前按 DefaultCharacter 建立。

因此出现了具有迷惑性的中间状态：

- 角色引用正确。
- UI 选择流程正确。
- 场景切换正确。
- 最终属性、生命和战斗效果错误。

这说明对缓存系统不能只验证输入引用，还必须验证最终产物和关键消费者。

### 原测试验证了理想顺序，没有验证真实顺序

原 CharacterSelectionTests 创建单独 PlayerStats，再手动调用 Awake。没有 PlayerHealth、PlayerMagnet 或子物体抢先读取属性，因此无法复现竞态。

原 MainMenu PlayMode 测试虽然真实加载 MainMenu 和 MainLevel，但加载后只读取 CharacterData.characterID，没有读取 MaxHealth、Might 等最终值，也没有检查 PlayerHealth.CurrentHealth。

测试数量增加不等于关键行为已覆盖。断言必须落在用户实际感知的结果上。

## 修复策略为什么不采用组件排序

可以通过 Script Execution Order 或调整 Inspector 组件顺序让 PlayerStats 更早运行，但这会把系统正确性绑定到编辑器配置：

- 新增子物体组件后可能再次破坏顺序。
- Prefab 和场景的组件排列可能不同。
- 测试对象和正式对象的生命周期不完全一致。
- 问题会在未来重构时以更隐蔽方式复发。

因此本次选择让 PlayerStats 的惰性初始化本身具备顺序安全性，而不是依赖外部排序。

## 做得好的地方

- 角色基础值、修改器、最终快照和 UI 展示职责清楚。
- 武器属性通过 WeaponBase 统一接入，没有在五类武器中重复散落计算公式。
- 池化投射物保存 Area 快照并在禁用时恢复尺寸，避免倍率跨生命周期累积。
- 老大的实际游玩反馈及时暴露了自动化遗漏，没有把“测试文件存在”误认为交付完成。
- 修复后同时补了精确顺序回归和真实场景最终值回归。
- 完整门禁达到 EditMode 40/40、PlayMode 16/16，并成功生成最新 Windows 独立构建。

## 仍然存在的风险与不足

### 角色内容仍不完整

当前角色选择会改变基础属性，但不会替换 MainLevel 中的玩家 Sprite、Animator、碰撞体或完整角色 Prefab。初始武器和固有能力仍为占位内容。

后续不能只向 CharacterDataSO 堆叠更多字段；应先决定采用统一 Player Prefab 加皮肤/配置，还是按角色使用独立 Prefab，再制定生命条锚点、动画事件和碰撞体规范。

### 21 项属性只有部分已产生玩法效果

目前实际接入的是生命、恢复、护甲、移动、六项武器属性、成长和磁吸。Luck、Greed、Curse、Revival、Reroll、Skip、Banish、Charm、Defang 仍主要是数据和展示能力。

这些属性需要各自的权威系统，不能由属性面板本身承担规则。

### 修改器还没有正式内容来源

SetModifiers/RemoveModifiers 已具备稳定来源语义，但正式能力、被动装备和临时 Buff 尚未调用它们。目前主要调用者仍是 F9 调试面板和自动化测试。

下一阶段应至少完成一个正式能力从数据资产到 PlayerStats sourceId 的端到端样例，再扩展能力栏。

### 独立构建的图形验收仍需人工完成

Windows 64 位构建成功且能无窗口稳定启动，但 Null GPU 会让 URP/TMP Shader 报不支持，不能据此判断真实画面。

此外，msyh SDF 缺少 U+00B7“·”，InputHint 和 Tagline 会把该字符替换为空格。该问题不阻塞属性修复，但应在下一轮 UI 字体整理中处理。

## 可复用的工程经验

1. Unity 生命周期函数顺序不应成为跨组件业务正确性的隐式依赖。
2. 惰性缓存的初始化入口必须同时完成所有前置状态解析，不能在 Awake 和属性 Getter 中走两套不一致路径。
3. 测试缓存系统时，应覆盖“消费者先访问、生产者生命周期后执行”的逆序场景。
4. 跨场景流程测试必须同时验证选择输入、运行时最终值和至少一个真实消费者。
5. ScriptableObject 引用正确只说明数据源选择正确，不说明缓存、快照或下游状态已同步。
6. 独立构建、无图形自动化和人工 Game 视图验收是三种不同证据，不能相互冒充。

## 会话结论

Session 12 已经把项目从单一默认玩家推进到可选择角色、可配置基础属性、可聚合修改器并由生命/移动/武器/UI 共同消费的统一框架。

本次最关键的修复不是一行数值调整，而是消除了角色选择对 Unity Awake 顺序的依赖，并把测试从“角色引用正确”提升到“最终属性和真实生命状态正确”。当前角色属性主干可以继续承载能力、被动装备和更多角色内容，但正式内容来源、角色外观切换和剩余属性规则仍需后续迭代。
